Orden de los scripts
Los <script> van al final del <body> (igual que vimos con Bootstrap en la Sesión 5): así el HTML ya existe en el DOM cuando JavaScript intenta buscarlo con querySelector. Si los ponés en el <head> sin más cuidado, muchas veces JS no va a encontrar los elementos todavía y vas a obtener null.

Cómo se enlazan HTML, CSS y JavaScript

Para seleccionar elementos del DOM y escuchar eventos queda la pregunta que más traba cuando se arma la primera web: ¿dónde escribo cada cosa y cómo hago que este botón haga algo? Un botón no "sabe" JavaScript: hay que cablearlo. En esta sección vas a ver el cableado completo, pieza por pieza, y con una demo real incluida en esta misma página.

La idea en una frase
HTML es la estructura, CSS la apariencia y JS el comportamiento. Se comunican por dos canales y solo dos: el atributo class conecta HTML con CSS, y el atributo id conecta HTML con JavaScript. Si los nombres no coinciden exactamente, el enlace no existe: no aparece ningún error de sintaxis, simplemente no pasa nada.

1. Tres archivos, tres responsabilidades, dos etiquetas de enlace

catalogo/
├── catalogo.html ← estructura + los ganchos (id y class)
├── estilos.css ← apariencia; se engancha por class
└── app.js ← comportamiento; se engancha por id
Archivo Qué aporta Cómo se enlaza Si falta
.html La estructura: cajas, textos, botones, inputs. Es el archivo que abrís en el navegador; contiene los dos enlaces. No hay página.
.css La apariencia: colores, tamaños, grillas, estados. <link rel="stylesheet" href="estilos.css"> dentro del <head>. La web se ve como un documento de texto sin estilos.
.js El comportamiento: leer inputs, reaccionar a clicks, crear HTML. <script src="app.js"></script> al final del <body>. La web se ve bien pero no reacciona a nada.

  <link rel="stylesheet" href="estilos.css">
</head>

Las rutas tienen que existir
href="estilos.css" significa "en la misma carpeta que este HTML". Si tu CSS está dentro de una carpeta css/, la ruta correcta es href="css/estilos.css", y si el JS está en js/, entonces src="js/app.js". Abrí F12 → pestaña Network y recargá: si ves un 404 en estilos.css o app.js, el navegador está buscando el archivo en un lugar donde no está — y por eso "no funciona nada".

2. El contrato de nombres: id y class

Un mismo elemento HTML tiene dos identificadores, y cada uno le habla a un lenguaje distinto. Mirá el mismo botón visto desde los tres archivos:

un mismo nombre escrito en los tres archivos 
<!-- 1) HTML: el botón lleva id (para JS) y class (para CSS) -->
<button id="btn-saludar" class="btn-primario">Saludar</button>

/* 2) CSS: se engancha por la CLASE, con un punto delante */
.btn-primario {
  background: #4fd1c5;
  color: #06141a;
  border-radius: 8px;
}
.btn-primario:hover { filter: brightness(1.1); }

// 3) JS: se engancha por el ID, con una almohadilla delante (#)
const boton = document.querySelector('#btn-saludar'); // ← mismo nombre, sin class

boton.addEventListener('click', () => {
  // acá va lo que tiene que pasar al tocar el botón
});
La regla del nombre exacto
En el HTML escribís id="btn-saludar" (sin símbolos). En JavaScript lo buscás como '#btn-saludar' (con #). En el HTML escribís class="btn-primario". En CSS lo estilás como .btn-primario (con .). Es el mismo criterio que ya usás para los selectores CSS desde la Sesión 1: # es id y . es class.

3. Qué propiedad de JS lee cada control de HTML

Esta es la tabla que resuelve el 90% de las dudas de "cómo conecto el HTML con JS". Cada control tiene una propiedad para leerlo y un evento que avisa cuándo cambió:

Elemento HTML Cómo lo leo / modifico Evento típico
<button id="btn"> document.querySelector('#btn') y le agrego un listener (no se "lee" ningún valor: solo se escucha el click). click
<input type="text"> input.value — el texto escrito, siempre como string. input (cada tecla) / change (al salir del campo)
<input type="number"> input.value + parseFloat() o parseInt() para convertirlo en número. input / change
<input type="checkbox"> input.checked — true o false. change
<select> select.value — el value de la <option> elegida. change
<textarea> textarea.value — el texto completo del área. input
<form> form.addEventListener('submit', …) + event.preventDefault() como primera línea. submit
<h3>, <p>, <span> el.textContent = 'texto' — escribe el contenido (seguro, no interpreta HTML). —
<img> img.setAttribute('src', url) y img.setAttribute('alt', texto). —
Cualquier elemento el.classList.add('x') / .remove('x') / .toggle('x') — así JS activa una regla CSS. —

4. La receta de 4 pasos para conectar cualquier control

No hace falta memorizar nada más: todos los enlaces de esta sesión (y de tu proyecto final) siguen siempre los mismos cuatro pasos.

  1. 1
    Poné un id en el HTML A cada elemento que JS tenga que encontrar: <button id="btn-saludar">. El id es único: no se repite en la página.
  2. 2
    Traé el elemento con querySelector const boton = document.querySelector('#btn-saludar'); — mismo nombre, con #. Se hace una sola vez, al inicio del archivo.
  3. 3
    Escuchá el evento con addEventListener boton.addEventListener('click', () => { … }); — el código de adentro no corre ahora, corre cuando el usuario actúa. Ese es el enlace.
  4. 4
    Dentro del callback: leé el input y escribí el DOM Leés con input.value, cambiás con salida.textContent y activás una clase CSS con salida.classList.add('destacado').

5. El ciclo completo: qué pasa cuando el usuario hace clic

# Quién actúa Qué ocurre
1 HTML El navegador lee el archivo y construye el árbol del DOM. Cada id queda registrado.
2 CSS Aplica un estilo a cada elemento según su class/selector. El botón se ve como botón.
3 JS Al cargar, busca los elementos por id y les cuelga un addEventListener. Ahí queda "cableado".
4 Usuario Hace clic. El navegador emite el evento click sobre ese elemento.
5 JS Su callback se ejecuta: lee .value, calcula, y escribe en el DOM (textContent, classList, createElement).
6 CSS El navegador repinta solo la parte que cambió, aplicando los estilos correspondientes al nuevo contenido o a la nueva clase.
Por qué conviene cambiar clases y no estilos sueltos
Cuando JS hace salida.classList.add('destacado'), los colores y tamaños siguen viviendo en el CSS. Si mañana querés cambiar el diseño, editás una sola regla CSS y todos los elementos cambian. Si en cambio hacés salida.style.background = '#4fd1c5' desde JS, el estilo queda "incrustado" en el archivo equivocado y se vuelve difícil de mantener. Regla práctica: JS decide cuándo, CSS decide cómo se ve.

// PASO 1 — ESTADO: una variable que guarda el dato real
              //guardo en la variable "valor" el numero 0 para iniciar un contador desde cero
let valor = 0;

// PASO 2 — GANCHOS: traigo los elementos del HTML por su id (una sola vez)
// y guardo cada uno en una variable (pantalla, btnMas, inputPaso, etc)
const pantalla = document.querySelector('#valor');
const btnMas   = document.querySelector('#btn-mas');
const btnMenos = document.querySelector('#btn-menos');
const btnReset = document.querySelector('#btn-reset');
const inputPaso = document.querySelector('#paso');

// PASO 3 — RENDER: la única función que escribe en el DOM
function pintar() {
  pantalla.textContent = valor;                                  // escribe el número
  pantalla.classList.toggle('negativo', valor < 0);              // activa CSS si es negativo
}

// PASO 4 — EVENTOS: cada control queda cableado a una acción
btnMas.addEventListener('click', () => {
  valor += leerPaso();   // lee el input y suma
  pintar();              // vuelve a dibujar
});

btnMenos.addEventListener('click', () => {
  valor -= leerPaso();
  pintar();
});

btnReset.addEventListener('click', () => {
  valor = 0;
  pintar();
});

// Lee el input y devuelve un NÚMERO (los inputs siempre dan texto)
function leerPaso() {
  const n = parseInt(inputPaso.value, 10);
  return isNaN(n) || n < 1 ? 1 : n;   // si no es válido, salto de 1
}

// PRIMER DIBUJADO al cargar la página
pintar();
Leé el ejemplo en tres colores
Todo lo del ejemplo cae en uno de estos tres grupos: estado (let valor — el dato), enlace (querySelector + addEventListener — las cuatro conexiones entre HTML y JS) y pintado (pintar() — el único lugar que toca el DOM). Si en tu proyecto podés señalar esas tres partes, el cableado está bien hecho.

8. Si falta una pieza, esto es lo que ves

Los errores de enlace son los más frustrantes porque no siempre tiran error en consola. Esta tabla es tu primer lugar de consulta:

Síntoma Qué falta Cómo se arregla
La página se ve sin estilos (todo texto negro sobre blanco) El <link> al CSS no está, está mal escrito o la ruta no existe Revisar href y la ruta real del archivo (css/estilos.css vs estilos.css); verificar en F12 → Network que no haya 404
El botón no hace nada al hacer clic Falta el <script>, o el id del botón no coincide con el del querySelector Comparar letra por letra: id="btn-saludar" ↔ '#btn-saludar' (mismo guion, mismo singular)
Consola: "Cannot read properties of null (reading 'addEventListener')" querySelector devolvió null: no encontró el elemento Id mal escrito, o el <script> está en el <head> y corre antes de que exista el HTML
El input siempre llega vacío o el precio se muestra NaN Se leyó el elemento en vez de su valor, o no se convirtió el texto a número Usar input.value (no input) y parseFloat(input.value)
El formulario recarga la página event.preventDefault() ausente en el listener de 'submit' Primera línea del callback: event.preventDefault();
JS cambia la clase pero no se ve ningún cambio visual La clase no existe en el CSS, o el selector CSS está mal escrito (.destacado vs destacado) Escribir la regla en el CSS con el mismo nombre exacto, incluido el punto

<link rel="stylesheet" href="estilos.css">
...

Por qué funciona: el id es el mismo en el HTML y en el querySelector (#mensaje, #btn-color); el addEventListener es el cable que une el clic con la función; y la clase resaltado existe en el CSS con el mismo nombre, así que cuando JS la activa el navegador aplica el estilo. descripcion string Texto breve debajo del nombre.
precio number Valor numérico (nunca con el símbolo $ incluido: eso se agrega al mostrarlo).
stock number Cantidad disponible; útil para alertas de "stock bajo".

Las 5 reglas del formato JSON

El bloque de arriba es un archivo de texto, no código JavaScript. Si pegás ese texto dentro de un .js sin tocarlo, el navegador tira SyntaxError: Unexpected token y no ejecuta nada. Estas son las cinco reglas que explican por qué, y son las que hacen que un JSON sea legible por cualquier lenguaje (PHP, Python, Java) y no solo por JavaScript.

Regla JSON válido Inválido, y por qué
Las claves van siempre entre comillas dobles "precio": 79.99 precio: 79.99 — en JSON la clave sin comillas no existe. En un objeto de JavaScript sí se permite: ahí está la primera diferencia.
Solo comillas dobles, nunca simples "nombre": "Teclado" 'nombre': 'Teclado' — las simples son válidas en JS pero ilegales en JSON.
No existen los comentarios — // auriculares dentro del archivo lo rompe por completo.
No se permite coma en el último elemento { "id": 1 } { "id": 1, } — la "trailing comma" es tolerada por JS moderno, pero es error en JSON.
Solo seis tipos de valor string, number, boolean, null, array, object undefined, funciones, Date, NaN e Infinity no existen en JSON: un undefined desaparece al serializar.

Como el JSON es solo texto, hay dos funciones que hacen todo el trabajo de frontera entre el mundo "texto" y el mundo "dato". Son las mismas que vas a usar el día que tu catálogo venga de una API real o de localStorage:

texto-vs-dato.js 
// 1) TEXTO -> DATO: "parsear" el texto para poder recorrerlo
const textoJson = '[{ "id": 1, "nombre": "Mouse", "precio": 34.5, "stock": 40 }]';

const productos = JSON.parse(textoJson);          // ahora es un array de verdad
console.log(productos[0].nombre);                 // "Mouse"
console.log(typeof productos);                    // "object"
console.log(productos[0].precio * 2);             // 69   (ya se puede calcular)

// 2) DATO -> TEXTO: "serializar" para guardar o enviar
const otraVezTexto = JSON.stringify(productos);
console.log(otraVezTexto);
// '[{"id":1,"nombre":"Mouse","precio":34.5,"stock":40}]'
Regla mental: parse de texto a dato, stringify de dato a texto
JSON.stringify siempre devuelve un string (lo notás porque typeof dice "string"), aunque por dentro tenga objetos. Y JSON.parse siempre devuelve un dato (array u objeto). Si te equivocás de dirección, recibís Unexpected token o in JSON at position 1: eso significa que le pasaste a parse algo que ya era un objeto, no un texto.
¿Y el fetch? ¿No deberíamos "consumir" un JSON?
En esta sesión el array vive en memoria, dentro de productos.js (como muestra el esqueleto de la sección 2). La razón es pedagógica: fetch es asíncrono —devuelve una Promise y su resultado llega "más tarde"—, y eso obliga a entender await, .then() y manejo de errores antes de poder practicar el CRUD. Con el array en memoria podés dominar hoy la parte difícil (DOM + estado + operaciones) y conectar el backend cambiando una sola función: en lugar de leer el array, lo pedís con fetch('productos.json') y hacés JSON.parse (o response.json()) con el mismo dato de salida. El resto del código no cambia.
Analogía
Pensá el JSON como una planilla de Excel exportada a texto: cada fila es un producto (un objeto { }), y cada columna es una propiedad (nombre, precio...). El array [ ] que envuelve todo es simplemente "la planilla completa": una lista ordenada de filas.

1. Qué es JavaScript y quién lo ejecuta

JavaScript es un lenguaje de programación interpretado y de tipado dinámico. "Interpretado" significa que no compilás un ejecutable: hay un programa —el motor— que lee el texto y lo ejecuta. En Chrome y Edge ese motor es V8, en Firefox es SpiderMonkey, en Safari es JavaScriptCore. "De tipado dinámico" significa que el tipo lo tiene el valor, no la variable: la misma variable puede guardar un número hoy y un texto mañana.

Contexto Qué puede hacer JS Qué NO puede hacer
Navegador (cliente) — lo de esta sesión Leer y modificar el DOM, escuchar eventos, guardar en localStorage, hacer pedidos HTTP con fetch, usar la cámara o el micrófono (con permiso). Leer archivos del disco sin que el usuario los elija, escribir en el sistema, abrir conexiones a bases de datos, ejecutar programas. Todo eso pasa por un servidor.
Node.js (servidor) Leer y escribir archivos, atender conexiones, hablar con bases de datos. Es el mismo lenguaje, otro entorno. No tiene DOM: no existe document.
Por qué el <script> va al final del <body>
El navegador es secuencial con los <script> clásicos: cuando llega a uno, deja de leer el HTML, lo ejecuta entero, y recién después sigue. Si ponés el script en el <head>, en ese momento el <body> todavía no existe, así que document.querySelector('#buscador') devuelve null y todo el cableado falla. Al final del <body> el árbol ya está construido. (La alternativa moderna es <script defer src="app.js"> en el <head>: se descarga en paralelo y se ejecuta después de parsear el HTML. El resultado es el mismo; el orden de las llamadas es idéntico.)

2. Variables: let, const y la vieja var

Una variable es un nombre que apunta a un valor en memoria. JavaScript tiene tres formas de declararla y solo dos se usan hoy:

Declaración ¿Se puede reasignar? Alcance Cuándo usarla
const No. Reasignar lanza TypeError. Bloque { } en el que se declara (alcance de bloque, block scope). Por defecto, para casi todo: referencias al DOM, funciones, objetos y arrays que no se van a reemplazar enteros.
let Sí. Bloque. Solo cuando el valor va a cambiar de nombre a nombre: un contador, un acumulador, el array productos (porque Delete lo reemplaza con filter).
var Sí. Función completa (function scope) y se "eleva" al inicio (hoisting) valiendo undefined. Nunca en código nuevo. Es JavaScript de los años 90: sus reglas de alcance causan bugs que no se ven.

4. Verdadero y falso: la tabla que explica todos los if

JavaScript no exige que la condición de un if sea un boolean. Cualquier valor se evalúa como verdadero o falso: son los valores truthy y falsy. Conocer la lista de falsy evita la mitad de los bugs.

Siempre FALSO (falsy) Siempre VERDADERO (truthy)

5. Igualdad: =, == y ===

Es el error más silencioso del lenguaje y el que protagoniza el Ejercicio 3 de "Detectá el error". No hay que memorizar: hay que entender que son tres operadores distintos.

Operador Nombre Qué hace Ejemplo
= Asignación Guarda el valor de la derecha en lo de la izquierda. Y cuando se usa dentro de una expresión, "devuelve" ese valor asignado. p.id = 7 deja la propiedad en 7 y la expresión vale 7.
== Igualdad débil Compara convirtiendo tipos: primero transforma y después compara. Es la fuente de resultados absurdos. "7" == 7 → true; 0 == "" → true; null == undefined → true.
=== Igualdad estricta Compara valor y tipo, sin conversiones. Es el que se usa siempre. "7" === 7 → false; 7 === 7 → true.
!== Desigualdad estricta Lo contrario de ===. Es el que usa Delete. p.id !== id → se queda con los que no son ese id.
Por qué findIndex((p) => p.id = id) siempre "edita el último"
Con un solo = no estás preguntando: estás asignando id a p.id en cada vuelta, y el valor que devuelve la expresión es ese mismo id. Si id es un número distinto de cero, el callback devuelve un valor truthy en la primera vuelta… y findIndex corta ahí y devuelve 0. Si el id buscado fuera 0, devuelve -1 (nunca encontró). Y de paso: todos los p.id del array quedaron pisados. Un solo carácter produce un bug que no tira error y corrompe los datos. Verificalo vos mismo en la consola con findIndex((p) => p.id = 2) sobre tres productos: devuelve 0.

8. Funciones: la unidad de trabajo

Una función es un bloque de código con nombre que recibe datos (parámetros), hace algo y puede devolver un resultado con return. En este proyecto hay funciones que devuelven un valor (find dentro de un callback) y funciones que no devuelven nada porque su trabajo es producir un efecto: escribir en el DOM (renderizarCatalogo) o avisar algo (agregarProducto).

funciones.js — las tres formas de escribir la misma idea 
// (A) DECLARACIÓN: tiene nombre y se puede llamar antes de su línea

}
console.log(calcularTotal(34.5, 3));   // 103.5

// (B) EXPRESIÓN: la función es el VALOR de una variable

// (C) ARROW FUNCTION: misma cosa, sintaxis corta (la que usamos en la sesión)

// Si tiene más de una línea, hacen falta llaves y return explícito:

La guard clause: la técnica que hace legibles las funciones CRUD
Es un return temprano que corta la función cuando los datos no sirven, para no anidar todo el resto dentro de un if. Comparalo:
Sin guard clause: if (datosValidos) { ...12 líneas adentro... }
Con guard clause: if (!datosValidos) return; y las 12 líneas quedan al ras, sin indentación. Es el patrón de agregarProducto en la Fase 5 y de if (!confirmado) return; en Delete. return sin valor devuelve undefined y sale de la función en ese mismo instante.

9. Callbacks y closures: por qué producto sigue existiendo dentro del listener

Un callback es una función que se entrega a otra función para que la ejecute más tarde. Eso es literalmente lo que hacés cuando escribís boton.addEventListener('click', () => { ... }): el código de adentro no corre ahora, corre cuando el usuario hace clic. Y un closure es la capacidad de esa función de recordar las variables del lugar donde fue creada, aunque ese lugar ya no se esté ejecutando.

callbacks-closures.js 
const productos = [
  { id: 1, nombre: 'Mouse' },
  { id: 2, nombre: 'Teclado' }
];

productos.forEach((producto) => {
  // 'producto' es el PARÁMETRO del callback: en cada vuelta vale un objeto distinto

  const boton = document.createElement('button');
  boton.textContent = 'Comprar ' + producto.nombre;

  boton.addEventListener('click', () => {
    // CLOSURE: este callback guarda una referencia al 'producto' de SU vuelta.
    // Los dos botones comparten la misma función en el código,
    // pero cada ejecución conserva su propio 'producto'.
    console.log('Compraste:', producto.nombre);
  });

  document.body.appendChild(boton);
});

// Con 'var' esto se rompería (todos los botones verían el ÚLTIMO producto),
// porque var no tiene alcance de bloque. Con let/const y parámetros, no.
Por qué en el Ejercicio 3 no hace falta leer dataset
Como el addEventListener se define dentro del forEach, cada botón queda "atado" a su propio producto por closure. Por eso console.log(producto.id) dentro del listener siempre imprime el id correcto. dataset es necesario en el otro patrón: cuando hay un solo listener en el contenedor (delegación) que atiende clicks de tarjetas que todavía no existían al momento de cablearlo. Las dos técnicas son válidas; conviene entender cuándo sirve cada una.

2 Fase 2 — Manipulación del DOM: renderizado

El DOM (Document Object Model) es la representación del HTML como un árbol de objetos que JavaScript puede leer y modificar. Vamos a usarlo para generar las tarjetas de producto en lugar de escribirlas a mano.

El DOM es un árbol, no un texto

Cuando el navegador termina de leer el HTML no guarda el texto: lo convierte en un árbol de objetos en memoria (Document Object Model). Cada etiqueta pasa a ser un nodo con propiedades y métodos, y document es la raíz de ese árbol. JavaScript no "edita el HTML": modifica esos objetos, y el navegador se encarga de redibujar la pantalla.

app.js — función renderizarCatalogo() 
const contenedor = document.querySelector('#contenedor-productos');

function renderizarCatalogo(productos) {
  // 1. Limpiar el contenedor antes de volver a dibujar (evita duplicados)
  contenedor.innerHTML = '';

  // 2. Recorrer el array con forEach y crear una tarjeta por producto
  productos.forEach((producto) => {
    const tarjeta = document.createElement('article');
    // CLASE "producto-card" — EL INSTRUCTOR APLICARÁ ESTILOS CSS AQUÍ
    tarjeta.classList.add('producto-card');

    const imagen = document.createElement('img');
    imagen.classList.add('producto-imagen');
    imagen.setAttribute('src', producto.imagen);
    imagen.setAttribute('alt', producto.nombre);

    const nombre = document.createElement('h3');
    nombre.classList.add('producto-nombre');
    nombre.textContent = producto.nombre;

    const precio = document.createElement('p');
    precio.classList.add('producto-precio');
    precio.textContent = `$${producto.precio.toFixed(2)}`;

    // 3. Insertar los hijos dentro de la tarjeta, y la tarjeta en el contenedor
    tarjeta.append(imagen, nombre, precio);
    contenedor.appendChild(tarjeta);
  });
}

Anatomía de renderizarCatalogo: qué hace cada línea

La función completa son tres fases y siempre el mismo orden: limpiar, crear e insertar. Si respetás ese orden, no hay tarjetas duplicadas ni elementos invisibles.

  1. 1
    contenedor.innerHTML = ''; Vacía el contenedor antes de volver a dibujar. Sin esta línea, cada filtro o cada alta agrega las tarjetas nuevas debajo de las viejas y la lista crece sin control. Es la causa número uno de "se me duplican los productos".
  2. 2
    productos.forEach((producto) => { ... }) Recorre el array y ejecuta el callback una vez por producto. El parámetro producto es una referencia al objeto real del array, no una copia: si lo modificaras, modificarías el estado.
  3. 3
    document.createElement('article') Crea un nodo huérfano: existe en la variable tarjeta, todavía no está en la página. Podés llenarlo de hijos con tranquilidad: el navegador no repinta hasta que lo insertás, así que no hay parpadeos.
  4. 4
    classList.add('producto-card') y dataset.id = producto.id Acá se cumple el contrato con CSS (la clase) y con los eventos (el data-id). Fijate que el JS nunca escribe colores ni tamaños: solo nombres de clase que el CSS ya conoce.
  5. 5
    textContent = ... y setAttribute('src', ...) Escriben el contenido. textContent trata todo como texto (seguro con datos de un formulario); setAttribute es para atributos como src, alt o href.
  6. 6
    tarjeta.append(...) y contenedor.appendChild(tarjeta) Primero los hijos dentro de la tarjeta, y al final la tarjeta dentro del contenedor. Ese último appendChild es el que "publica" todo el subárbol de golpe.
Forma de escribir contenido Qué hace Riesgo
el.textContent = 'Hola' Inserta texto literal. Si escribís <b>Hola</b> se ve tal cual. Ninguno. Es la opción por defecto.
el.innerHTML = '<b>Hola</b>' Interpreta el string como HTML y lo convierte en nodos hijos. Si el string contiene datos del usuario, permite inyectar <script> o <img onerror="..."> (XSS). Solo con texto propio y controlado.
el.innerHTML = '' Elimina todos los hijos. Es la forma idiomática de "limpiar". Ninguno con string vacío. (Alternativa: el.replaceChildren().)
el.append(nodo) / appendChild(nodo) Inserta nodos (no strings). append acepta varios y también texto; appendChild solo uno y solo nodos. Ninguno.
Por qué se vuelve a dibujar todo y no solo lo que cambió
Este es el patrón render declarativo: la pantalla es una función del estado (pantalla = f(productos)), así que cada cambio se resuelve borrando y volviendo a dibujar. Es más simple y mucho menos propenso a errores que intentar "parchear" la tarjeta justa. Con 14 productos el costo es imperceptible (milisegundos). Cuando la lista crece a miles, se optimiza con DocumentFragment (armar todo fuera del DOM y pegar una sola vez) o con virtual DOM (lo que hacen React y Vue). Aprender el patrón simple primero es lo que te permite después entender por qué existe el otro.
El patrón de tres pasos, memorizable
Cada elemento nuevo de la tarjeta sigue siempre lo mismo: (1) crear → (2) configurar (clase, contenido, atributos, listener) → (3) insertar en el padre. Si te trabás armando una tarjeta, escribí esos tres pasos como comentarios y completalos: no hay otra forma de hacerlo.

3 Fase 3 — Eventos e interactividad

Un sitio dinámico reacciona a lo que hace el usuario. Para eso usamos addEventListener, que "escucha" una acción (click, submit, input) y ejecuta una función cuando ocurre.

Qué es un evento y qué viaja dentro de él

Un evento no es una llamada de HTML a JavaScript: es un aviso que emite el navegador cuando algo pasa (un clic, una tecla, el envío de un formulario, la carga de una imagen). addEventListener(tipo, callback) registra un escucha: le dice al navegador "cuando emitas este tipo de evento sobre este elemento, ejecutá esta función". El navegador le pasa al callback un objeto con toda la información del suceso. Ese objeto se llama event (o e, o evt: el nombre lo elegís vos, es solo el parámetro).

Propiedad / método de event Qué contiene Uso en esta sesión
event.type El nombre del evento: "click", "submit", "input". Depuración.
event.target El elemento más profundo que recibió el evento (el que realmente tocó el usuario). event.target.closest('.producto-card') para saber a qué tarjeta pertenece el botón.
event.currentTarget El elemento donde está registrado el listener. Con delegación: el contenedor, no el botón.
event.preventDefault() Cancela la acción por defecto del navegador para ese evento. Evita que el <form> recargue la página al hacer submit.
event.stopPropagation() Detiene el burbujeo: el evento no sigue subiendo a los padres. Casi nunca hace falta; no es lo mismo que preventDefault.
event.target.value El valor actual del control que disparó el evento. Leer un input en vivo dentro del listener de 'input'.

¿Por qué hay dos "targets"? Porque los eventos burbujean. Cuando tocás el ícono dentro de un botón, el evento nace en el ícono y sube por todos sus ancestros hasta document, ejecutando los listeners que encuentre en el camino:

// UN listener en el contenedor atiende a TODAS las tarjetas presentes
// y futuras. Fundamental: las tarjetas se recrean en cada render,

contenedor.addEventListener('click', (event) => {

  eliminarProducto(id);

onclick="..." en el HTML vs addEventListener
<button onclick="eliminar(3)"> funciona y por eso tienta: es corto. Pero tiene tres problemas serios. (1) Se pisa: si asignás onclick dos veces, la segunda reemplaza a la primera; addEventListener en cambio acumula. (2) Mezcla capas: volvés a meter comportamiento en el HTML, justo lo que separamos en la sección 3. (3) No hay closure ni acceso al evento real, y el código escrito ahí vive en el ámbito global: no ve tus variables. Por eso todo el cableado de esta sesión va por addEventListener.
Evento / método Cuándo se usa
'click' Botones: Agregar, Editar, Eliminar.
'submit' Cuando se envía un <form> (al tocar "Guardar").
'input' Cada tecla que se escribe en un campo de texto (ideal para búsqueda en vivo).
event.preventDefault() Evita el comportamiento por defecto del navegador (recargar la página al enviar un form).
event.target Referencia al elemento exacto que disparó el evento (útil con varios botones iguales).

Lectura del código de eventos, línea por línea

Fragmento Qué ocurre exactamente
buscador.addEventListener('input', ...) 'input' se dispara en cada cambio del valor: al escribir, al pegar, al borrar con retroceso, al usar el autocompletado. Es lo que permite una búsqueda en vivo sin apretar "Buscar". Si usaras 'change', la búsqueda recién correría al salir del campo, y la sensación sería lenta.
formulario.addEventListener('submit', ...) Se dispara al enviar el form: por el botón type="submit" o al apretar Enter dentro de un campo. Fijate que no escuchamos el click del botón: escuchamos el submit del formulario, que cubre los dos caminos.
event.preventDefault(); Primera línea del callback, siempre. Cancela la navegación por defecto (recargar o ir a la URL de action). Sin ella, el navegador descarga la página de nuevo y todo el array en memoria se pierde: parece que "el producto no se agregó".
querySelectorAll('.btn-eliminar').forEach(...) Trae todos los botones y les cuelga un listener a cada uno. Funciona, pero solo con los que existían en ese momento: las tarjetas que se dibujen después no quedan cableadas. Es la razón por la que el código final cablea los botones dentro de renderizarCatalogo, o usa delegación.
event.target.closest('.producto-card') Sube desde el elemento tocado hasta encontrar la tarjeta. Si el click no ocurrió dentro de una tarjeta, devuelve null — y ahí hay que cortar con una guard clause.

La trampa de dataset: todo lo que llega del HTML es texto

data-id="7" en el HTML se lee como tarjeta.dataset.id en JS, y el nombre se convierte a camelCase: data-producto-id pasa a ser dataset.productoId. Pero el valor siempre es un string, aunque en el HTML parezca un número. Y como === no convierte, comparar directo falla en silencio:

dataset-trampa.js 
// En el HTML:  <article class="producto-card" data-id="7">

const tarjeta = document.querySelector('.producto-card');

console.log(tarjeta.dataset.id);              // "7"     (string)
console.log(typeof tarjeta.dataset.id);       // "string"
console.log(tarjeta.dataset.id === 7);        // false   <- la trampa
console.log(tarjeta.dataset.id === '7');      // true
console.log(Number(tarjeta.dataset.id) === 7); // true   <- conversión explícita

// Consecuencia real: findIndex no encuentra nada y devuelve -1
const index = productos.findIndex((p) => p.id === tarjeta.dataset.id);
console.log(index);   // -1  aunque el producto exista

// LA SOLUCIÓN (una de las dos, no las dos):
const id = Number(tarjeta.dataset.id);
const indexOk = productos.findIndex((p) => p.id === id);
console.log(indexOk); // el índice real
Cómo no olvidarse nunca
Regla mnemotécnica: lo que viene del HTML o de un input es texto; lo que viene de tu array es número. En el momento en que un dato cruza la frontera HTML → JS, pasalo por Number(), parseInt() o parseFloat(). El código final lo hace en el listener del formulario: precio: parseFloat(...) y stock: parseInt(..., 10). Esa es la única razón por la que p.id === id funciona después.

4 Fase 4 — Consumo y manejo del JSON

Con el array de productos ya renderizado y los eventos básicos funcionando, ahora tratamos el JSON como lo que es: una base de datos en memoria que podemos consultar con los métodos de array de JavaScript.

Método Devuelve Uso típico
array.find(fn) El primer elemento que cumple la condición, o undefined. Buscar un producto por id para mostrar su detalle.
array.findIndex(fn) La posición (número) del primer elemento que cumple la condición, o -1. Ubicar un producto para reemplazarlo (Update).

Qué es un callback y por qué todos estos métodos lo piden

find, findIndex, filter y forEach hacen lo mismo por dentro: recorren el array y, en cada vuelta, llaman a la función que les pasaste. Esa función es el callback. Vos no la ejecutás: se la entregás al método y el método decide cuándo llamarla. Por eso p => p.id === 3 no se ejecuta en la línea donde lo escribís, sino una vez por cada producto.

El callback recibe tres argumentos (casi siempre usamos solo el primero, pero existen): (elemento, indice, arrayCompleto). Y lo que el callback devuelve es lo que el método interpreta: filter se queda con los que devolvieron un valor truthy; find devuelve el primero que lo hizo.

callback-en-detalle.js 
const productos = [
  { id: 1, nombre: 'Mouse', precio: 34.5, categoria: 'electronica' },
  { id: 2, nombre: 'Lámpara LED', precio: 22, categoria: 'hogar' },
  { id: 3, nombre: 'Teclado', precio: 129.99, categoria: 'electronica' }
];

// El callback recibe (elemento, indice, array) en cada vuelta:
productos.forEach((producto, indice) => {
  console.log(indice, producto.nombre);
});
// 0 "Mouse"   1 "Lámpara LED"   2 "Teclado"

// Equivalente a un bucle escrito a mano (para entender qué hace por dentro):
for (let i = 0; i < productos.length; i++) {
  const producto = productos[i];
  console.log(i, producto.nombre);
}
forEach no sirve para "cortar" ni para devolver
forEach siempre recorre todo el array y siempre devuelve undefined. No existe break: si escribís return dentro del callback, solo salís de esa vuelta y seguís con la próxima (se comporta como continue). Si necesitás detenerte al encontrar algo, usá find; si necesitás construir un valor nuevo, usá filter o map. Y si intentás const r = productos.forEach(...), r vale undefined: es el error de "no me devuelve nada" más común.

(1) Usar = en vez de === dentro del callback: no tira error, devuelve resultados absurdos (es el bug del Ejercicio 3 de "Detectá el error"). Analogía

5 Fase 5 — CRUD completo integrado

Llegó el momento central de la sesión: vamos a construir las 4 operaciones que cualquier sistema de datos necesita. Las cuatro comparten la misma lógica: modificar el array productos y después llamar a renderizarCatalogo(productos) para que la pantalla refleje el nuevo estado.

Antes de escribir el CRUD: identidad, mutabilidad y copias

Las cuatro operaciones fallan siempre por la misma razón: no se distingue entre modificar el array y reemplazarlo, ni entre copiar un valor y compartir una referencia. Son dos preguntas que hay que hacerse antes de escribir cada línea del CRUD:

Pregunta 1: ¿este método devuelve algo nuevo o modifica el array original? Pregunta 2: ¿esta variable guarda el valor o la dirección de memoria?

MUTAN el array original DEVUELVEN uno nuevo (no lo tocan)
push() (agrega al final), pop() (saca el último), unshift() (agrega al inicio), shift() (saca el primero), splice() (corta y pega en el medio), sort(), reverse() filter(), slice(), concat(), map(), spread ([...array]), find, findIndex, forEach (no devuelve nada, pero no muta)
referencias.js — el ejemplo que hay que correr en la consola 
// (1) Los objetos y arrays NO se copian al asignarlos: se comparte la referencia
const original = [{ id: 1 }];
const alias = original;          // no es una copia: es otro nombre para el MISMO array
alias.push({ id: 2 });
console.log(original.length);    // 2  <- cambió "el original" también
console.log(original === alias); // true <- son la misma dirección de memoria

// (2) Para copiar de verdad hay que crear otro array
const copia = [...original];     // copia SUPERFICIAL (los objetos de adentro se comparten)
copia.push({ id: 3 });
console.log(original.length);    // 2  <- ahora sí quedó intacto

// (3) filter SIEMPRE devuelve un array nuevo (con los mismos objetos adentro)
const sinDos = original.filter((p) => p.id !== 2);
console.log(original.length);    // 2  <- intacto
console.log(sinDos.length);      // 1

// (4) const impide REASIGNAR la variable, no MUTAR su contenido
const lista = [];
lista.push('a');                 // válido (mutación)
// lista = ['b'];                // ERROR: Assignment to constant variable (reasignación)

// (5) Comparar objetos compara REFERENCIAS, no contenido
console.log({ id: 1 } === { id: 1 });   // false <- son dos objetos distintos
const a = { id: 1 };
const b = a;
console.log(a === b);                   // true  <- el mismo objeto
Por qué Create usa push y Delete usa filter
No es capricho. push muta: agrega al final del mismo array y no devuelve nada útil. filter no puede mutar: construye un array nuevo, así que obliga a reasignar (productos = productos.filter(...)) y por eso el array se declara con let. Las dos formas son válidas; lo que no se puede es mezclarlas a ciegas. Si querés uniformidad total, podés escribir Create sin mutar: productos = [...productos, nuevoProducto];. Es el mismo resultado, con otro estilo.

Date.now(): de dónde sale el id nuevo (y cuándo falla)

Date.now() devuelve la cantidad de milisegundos transcurridos desde el 1 de enero de 1970 (la "época" de Unix). Es un número enorme que cambia en cada llamada, y por eso se usa como id: dos productos creados con milisegundos de diferencia tienen ids distintos. Su ventaja es que no hay que gestionar un contador; su límite es que no es garantía de unicidad: dos altas en el mismo milisegundo programático (un bucle, un test, un doble clic muy afortunado) pueden producir el mismo número. Para un laboratorio alcanza y sobra; para un sistema real se usa un id del backend o crypto.randomUUID().

ids.js — las dos formas de generar un id 
// FORMA 1 (la de la sesión): marca de tiempo en milisegundos
console.log(Date.now());   // 1792583877146

// FORMA 2 (más robusta): el id más alto que ya existe, más uno.
// Útil cuando el array viene de un JSON y no querés ids gigantes.
function siguienteId(lista) {
  let maximo = 0;
  lista.forEach((p) => {
    if (p.id > maximo) maximo = p.id;
  });
  return maximo + 1;
}

console.log(siguienteId([{ id: 7 }, { id: 12 }]));  // 13
console.log(siguienteId([]));                        // 1

// Con Math.max y spread se escribe más corto:
// Math.max(...lista.map((p) => p.id)) + 1
// (map es como forEach pero DEVUELVE un array nuevo con lo que retorna cada vuelta)
El spread copia solo el primer nivel
{ ...producto } crea un objeto nuevo, pero si el producto tuviera una propiedad que a su vez es un objeto o un array (por ejemplo dimensiones: { ancho: 10 }) esa propiedad sigue siendo la misma referencia en el original y en la copia. En este proyecto todas las propiedades son primitivas (string, number), así que el spread es una copia segura. Si algún día anidás objetos, necesitás una copia profunda (structuredClone(obj)).

5.3 UPDATE — Editar producto existente

Buscamos la posición del producto con findIndex y reemplazamos ese elemento del array combinando sus datos viejos con los nuevos usando el operador spread (...).

function editarProducto(id, datosActualizados) {
  const index = productos.findIndex((p) => p.id === id);

  if (index !== -1) {
    // Spread: mezcla el objeto viejo con los campos nuevos (los nuevos pisan a los viejos)
    productos[index] = { ...productos[index], ...datosActualizados };
    renderizarCatalogo(productos);
  } else {
    console.error('No se encontró ningún producto con id', id);
  }
}

5.4 DELETE — Eliminar producto

Pedimos confirmación con confirm() (una ventana nativa del navegador) y usamos filter para crear un array nuevo sin el producto eliminado.

function eliminarProducto(id) {
  const confirmado = confirm('¿Seguro que deseas eliminar este producto?');
  if (!confirmado) return; // el usuario canceló: no hacemos nada

  productos = productos.filter((p) => p.id !== id); // nuevo array sin ese producto

Create, Read, Update y Delete parecen cuatro cosas distintas, pero todas recorren el mismo circuito. Si lo memorizás una vez, no hay que memorizar nada más:

     ↓
[ evento ]   el navegador emite 'click' | 'submit' | 'input'
     ↓
[ listener ] el callback lee .value, llama a la función de lógica
     ↓
[ lógica ]   modifica el ESTADO: productos.push / productos[i] = / filter
     ↓

     ↓

Lectura de cada función

Código Qué hace, palabra por palabra
if (!datos.nombre || datos.nombre.trim() === '' || isNaN(datos.precio)) Tres condiciones unidas por || (basta que una sea verdadera): no vino el campo, o vino solo con espacios (trim() los saca y queda vacío), o el precio no es numérico. El ! de adelante convierte el string vacío (falsy) en true.
alert('...'); return; alert es una ventana nativa que bloquea la ejecución hasta que el usuario acepta. Devuelve undefined siempre. El return siguiente corta la función: sin él, alert mostraría el mensaje y el producto se guardaría igual.
{ id: Date.now(), ...datos } Crea un objeto nuevo cuyo primer par es el id, y después "desparrama" todas las propiedades de datos. Si datos trajera un id, el orden importa: lo que va después pisa lo de antes. Como id está primero, el Date.now() queda protegido… salvo que datos incluya id. En el código final no lo incluye.
const index = productos.findIndex(...) Guarda una posición (number), no el objeto. Si no encuentra, es -1. Nunca null, nunca undefined: siempre un número, y por eso se compara con !== -1.
productos[index] = { ...productos[index], ...datos } Reemplaza el elemento en esa posición. El spread primero copia el objeto viejo (todas sus propiedades), y el segundo spread pisa las que vengan en datosActualizados. Resultado: los campos que no mandaste se conservan. Es un reemplazo, no una mutación propiedad por propiedad.
console.error('No se encontró...', id) Igual que console.log pero en rojo y con la pila de llamadas. No detiene la ejecución: solo informa. Para detenerla de verdad se usa throw new Error(...).
if (!confirmado) return; confirm() devuelve un boolean: true si el usuario aceptó, false si canceló. El ! invierte: "si NO confirmó, salí". Es la guard clause más corta del proyecto y la que evita borrar por accidente.
productos = productos.filter((p) => p.id !== id) Se queda con todos los que no son ese id. El !== es lo que expresa "sin el eliminado": si escribieras ===, borrarías todos los demás.
Por qué toda operación termina en renderizarCatalogo(productos)
Porque la pantalla y el array son dos cosas distintas y hay que sincronizarlas a mano. El array cambia al instante; el DOM no se entera solo. Ese es el trabajo del render: es el único puente entre el estado y lo que se ve. Si te olvidás de llamarlo, el dato se modifica (lo comprobás con console.log(productos)) pero la pantalla queda vieja — el síntoma clásico de "lo borré pero sigue apareciendo".
¿Por qué eliminarProducto necesita let?
filter siempre devuelve un array nuevo; no modifica el original. Por eso, para que productos = productos.filter(...) sea válido, el array tiene que haberse declarado con let y no con const (una const no se puede reasignar).

Qué es un estado de interfaz: el caso editandoId

El código final guarda una variable que no es un dato del negocio, sino del estado de la pantalla: let editandoId = null;. Su valor responde a "¿el formulario está en modo crear o en modo editar?":

Un solo formulario, dos comportamientos, decididos por una variable booleana disfrazada de número. Esa es la técnica estándar; la alternativa sería tener dos formularios HTML distintos o duplicar código. Y de ahí salen los dos métodos de apoyo: formulario.reset() (devuelve todos los campos a su valor inicial: no toca el array ni el estado) y classList.add('open') / remove('open') (muestra u oculta el formulario delegando en la regla CSS de la clase .open — JavaScript decide cuándo, CSS decide cómo se ve, tal como se dijo en la sección 3).

Por qué el código final llama a aplicarFiltros() y no a renderizarCatalogo(productos)
Este es el detalle más fino de toda la sesión y el que separa un CRUD que "anda" de uno correcto. Si el usuario tiene escrito "monitor" en el buscador y agregás un teclado, tenés dos opciones: (a) renderizar todos los productos —el teclado aparece de golpe, contradiciendo el filtro activo— o (b) volver a calcular el filtro con el estado actualizado, y entonces el teclado nuevo simplemente no se muestra (porque no coincide con la búsqueda). La opción (b) es la correcta: el render siempre es una consecuencia del estado completo, incluido el de los controles de filtro.
Cómo depurar el flujo en 30 segundos
Poné un console.log con etiqueta en cada capa y mirá el orden de impresión en la consola: console.log('1 evento'), console.log('2 datos', datos), console.log('3 estado', productos), console.log('4 render', lista). Si el orden real no es 1→4, ya sabés en qué capa está el problema. Si el 3 muestra el array bien pero la pantalla no cambió, el problema está en el 4. Si el 2 trae datos vacíos, está en la lectura de los inputs. Con esa única técnica se resuelven casi todos los bugs de esta sesión.
Regla de oro
Ninguna función de lógica debería tocar el DOM directamente, y ninguna función de renderizado debería modificar el array de datos. Esta separación (a veces llamada "separación de responsabilidades") es lo que evita que un proyecto pequeño se vuelva imposible de depurar cuando crece.

function aplicarFiltros() {

Ejercicio 3 — Editar siempre falla

buggy-15.js 
function editarProducto(id, datosActualizados) {
  const index = productos.findIndex((p) => p.id = id);
  productos[index] = { ...productos[index], ...datosActualizados };
  renderizarCatalogo(productos);
}

🔎 Esta función siempre termina editando el último producto del array, sin importar qué id se le pase. Encontrá el 1 problema (es un error muy común y difícil de ver a simple vista).

Ver solución y explicación
  1. Dentro del findIndex se escribió p.id = id (un solo signo igual, que es asignación) en vez de p.id === id (triple igual, comparación). Como una asignación siempre "devuelve" el valor asignado (y id suele ser un número distinto de cero), la condición se evalúa como verdadera para el último elemento recorrido, haciendo que findIndex devuelva el último índice.

Tip de debugging: este es uno de los bugs más silenciosos de JavaScript porque no tira ningún error en consola. La única forma de detectarlo es revisar con atención cada comparación dentro de un find/ filter/findIndex, o agregar un console.log(p.id, id) dentro del callback para ver qué se está comparando realmente.

Los métodos que piden los desafíos, explicados

Los cinco desafíos usan cuatro herramientas que la sesión todavía no presentó. Van acá, con su detalle, para que puedas encararlos sin adivinar:

Método Qué hace ¿Muta el array? Detalle que hay que saber
sort(fn) Ordena los elementos. Sí (a diferencia de filter) Sin argumento ordena alfabéticamente: con [10, 9, 100] devuelve [10, 100, 9] porque compara texto. Para números hay que pasar el comparador (a, b) => a.precio - b.precio.
slice(inicio, fin) Devuelve una porción del array. No El fin queda excluido: slice(0, 5) devuelve 5 elementos (índices 0 a 4). Sin argumentos, devuelve una copia completa: es el otro modo de copiar un array.
reduce(fn, inicial) Recorre y acumula un único valor. No El callback recibe (acumulador, elemento) y lo que devuelve pasa a ser el acumulador de la vuelta siguiente. Siempre pasá el valor inicial (0 para sumas), o con un array vacío explota.

Las tres trampas de localStorage
(1) Si guardás sin stringify, lo que queda es "[object Object]" y al leerlo parse explota. (2) Si leés null (porque nunca guardaste nada) y lo pasás a JSON.parse, explota también: usá || '[]' como valor por defecto. (3) Los ids con Date.now() sobreviven bien, pero los number guardados vuelven como number (JSON respeta el tipo), mientras que undefined desaparece de la propiedad y al recuperarla ya no está. Nunca guardes estado que dependa de undefined.

Función que se pasa como argumento a otra función, para ejecutarse en un momento posterior (ej: dentro de forEach o addEventListener).
Spread (...)
Operador que copia las propiedades de un objeto (o elementos de un array) dentro de otro nuevo.
Estado (state)
Los datos que determinan lo que se muestra en pantalla en un momento dado; en esta sesión, el array productos.
Renderizar
Generar o actualizar el HTML visible a partir de los datos actuales del estado.
Objeto
Colección de pares clave/valor. Se escribe con llaves { } y sus propiedades se leen con punto o corchetes. En esta sesión, cada producto.
Array
Lista ordenada de elementos con índice numérico desde 0. Técnicamente es un objeto, por eso typeof [] devuelve "object".
Referencia
Dirección en memoria de un objeto o array. Dos variables con la misma referencia apuntan al mismo dato: modificar una modifica la otra. Los primitivos (string, number, boolean) se copian por valor.
Mutación
Modificar un array u objeto existente (push, splice, sort). No es lo mismo que reasignar: const permite mutar y prohíbe reasignar.
Closure
Capacidad de una función de recordar las variables del ámbito donde fue creada, aun después de que ese ámbito terminó. Explica por qué cada botón de una tarjeta recuerda su propio producto.
Truthy / falsy
Cómo se evalúa un valor en un contexto booleano. Son falsy: false, 0, "", null, undefined, NaN. Todo lo demás es truthy, incluido un array vacío.
Burbujeo (bubbling)
Propagación del evento desde el elemento que lo originó hacia sus ancestros. Es lo que permite escuchar en el contenedor los clicks de todos sus hijos.
Delegación de eventos
Técnica de poner un solo listener en un contenedor y averiguar dentro del callback cuál hijo fue tocado con event.target.closest(). Indispensable con listas que se re-renderizan.
Nodo (DOM)
Cada pieza del árbol del documento: un elemento, un texto, un comentario. Un nodo creado con createElement no está en la página hasta que se inserta con append.
Estado de interfaz
Dato que describe la pantalla, no el negocio: editandoId, si el formulario está abierto, qué filtro está activo. Suele vivir en variables separadas del estado principal.
